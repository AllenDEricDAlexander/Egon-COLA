# egon-cola-source-light-open

[English](README.md) | [中文](README.zh-CN.md)

`egon-cola-source-light-open` is the open-source edition of the Egon COLA Light archetype. It is one deployable Spring Boot 3.5.16 module. The package architecture remains the large-monolith, domain-first layout; `start`, `adapter`, `facade`, `application`, `domain`, `infrastructure`, and `common` are logical packages, not Maven modules.

## Stack

- Java 21, Spring Boot 3.5.16, Spring Cloud 2025.0.3, Spring Cloud Alibaba 2025.0.0.0, and Nacos 3.0.3.
- MyBatis-Plus through the Egon COLA Common MP starter, with DAO/XML SQL and EgonModel POs and ShardingSphere-JDBC 5.5.3.
- Egon COLA Common Core, Common ID, and Dynamic Thread Pool components.
- Springdoc OpenAPI 2.8.17 for HTTP API documentation; the Gateway is an external platform and is not generated here.
- RabbitMQ, Redis, GraphQL, and external HTTP clients remain optional integrations from the existing Light use cases.

## Domain-first structure

```text
src/main/java/top/egon/cola/archetype/source/lightopen
├── start              # startup assembly, OpenAPI, async and datasource config
├── adapter            # HTTP, GraphQL, MQ inbound and facade implementations
├── facade             # stable local application contracts and DTOs
├── application        # use-case orchestration, validation and transactions
├── domain             # aggregates, rules, services and repository ports
├── infrastructure     # MyBatis-Plus DAO/PO/ServiceImpl, clients, cache and MQ adapters
└── common             # business-neutral project primitives
```

The intended direction is `adapter -> application -> domain -> common`; `infrastructure` implements domain ports and `start` assembles the application. The generated `OpenArchitectureTest` enforces the inward direction and rejects persistence/transport framework dependencies from Domain and Application.

## IDs and persistence

Technical IDs are generated by the Common ID `LongIdGenerator` and stored as PostgreSQL `BIGINT`. Internal domain, application, persistence, and sharding values use positive `Long`; HTTP and GraphQL boundary values remain decimal strings. Set a unique `EGON_ID_MACHINE_ID` for every runtime instance; there is no runtime default.

Persistence uses the Egon COLA Common MP starter: domain services expose EgonColaIService contracts, while infrastructure owns EgonColaServiceImpl, DAO and EgonModel PO pairs. The generated project contains DAO interfaces, XML statements, and explicit affected-row checks. It does not create or update schema during application startup. Apply these files manually, in order, to every physical PostgreSQL target:

```text
src/main/resources/db/manual/postgresql/master-data/001__create_light_master_data_schema.sql
  src/main/resources/db/manual/postgresql/master-data/003__migrate_light_master_data_to_egon_model.sql
src/main/resources/db/manual/postgresql/shard/002__create_light_sharded_schema.sql
  src/main/resources/db/manual/postgresql/shard/004__migrate_light_sharded_to_tenant_model.sql
```

Read the adjacent `db/manual/postgresql/README.md` before applying SQL. The scripts are PostgreSQL-oriented, use `BIGINT` for technical IDs, and include operator verification and rollback guidance. H2 tests execute them only through an explicit test helper.

ShardingSphere routes `light_school_classes` and `light_class_course_schedules` by positive `tenant_id` with the stable positive-Long algorithm. Keep a class and its schedules on the same root key; cross-shard workflows require business idempotency and compensation owned by the caller.

## Runtime governance

Spring Boot's single `applicationTaskExecutor` is the only application async executor. Its environment-backed bounds default to core `8`, max `32`, queue `1000`, and keep-alive `60s`. `DtpTaskDecorator` propagates and cleans execution context, while the Dynamic Thread Pool component can govern the same executor through Redis in `dev` and `prod`.

The `test` profile sets `egon.cola.component.dtp.enabled=false`, disables DTP reporting and Nacos, uses H2, and disables RabbitMQ, Redis, and external HTTP integrations. Generated tests therefore require no live infrastructure. `dev` and `prod` compose examples pass the machine ID and DTP Redis/report settings explicitly.

## API and commands

Springdoc exposes the OpenAPI document at `/v3/api-docs` and Swagger UI at `/swagger-ui.html`.

```bash
# generated project
./mvnw -B -ntp clean verify
./mvnw -B -ntp -DskipTests package
```

`verify` includes the generated ArchUnit rules. `test` and `verify` are static/generated-project checks; they do not prove a live Nacos, Redis, PostgreSQL, RabbitMQ, or external service topology.

## Container delivery

Use the environment examples and one of the six Compose variants:

```bash
docker compose --env-file deploy/env/.env.example \
  -f deploy/compose/compose.docker.yaml up -d --build
```

The dev and production examples use Nacos `nacos/nacos-server:v3.0.3`. Provide database credentials, Redis/RabbitMQ credentials, Nacos credentials, and a unique `EGON_ID_MACHINE_ID` through the operator-owned environment file. This repository does not start the application or execute database SQL as part of archetype generation.

For encryption, use the existing `ConfigCipherCli` with `EGON_CONFIG_DECRYPT_KEY` or `EGON_CONFIG_DECRYPT_KEY_FILE`; never commit credentials or keys.
