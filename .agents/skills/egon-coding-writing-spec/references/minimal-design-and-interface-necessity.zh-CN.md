## 最小自洽设计规则

从满足用户可见需求、保持正确性且最符合仓库现状的最小方案开始。基准方案必须优先复用语义已经一致的现有契约、上下文、组件、模型和基础设施。

只有 Spec 指出简单方案无法满足的具体需求或约束时，才能选择更复杂的方案。“更整洁”“更灵活”“面向未来”“解耦”或“最佳实践”如果没有当前变化点和证据，都不足以支持复杂度。

使用以下支配规则：

```text
如果方案 A 与方案 B 满足同一组已批准需求，
且 A 引入更少契约、状态、依赖、网络调用、失败点或迁移义务，
则必须选择 A，除非 B 具有当前需求明确要求的实质优势。
```

不能因为模板存在某个章节就扩大范围。详细文档用于描述已选方案，不能反过来证明方案必须更大。

## 元素必要性审核

绘制目标架构前，先清点每个新增或实质扩展的设计元素：

| 拟议元素 | 变更 | 需求 | 现有/直接方案 | 直接方案的具体不足 | 新增成本与失败模式 | 结论 |
| --- | --- | --- | --- | --- | --- | --- |
| `<API/类/表/缓存/Job/分层/依赖>` | 新增 / 扩展 / 保留 / 删除 | `REQ-001` | `<复用/派生/直接路径>` | `<有证据缺口或 None>` | `<耦合/状态/RTT/运维/迁移>` | Add / Keep / Merge / Remove |

审核范围包括：

- 公共/内部 HTTP、RPC 和事件契约；
- Metadata、Selector、Lookup、Validation、Preview 和 Capability 接口；
- Service 接口/实现、Helper、Adapter、Factory、Strategy 和 Facade；
- Request/Response/DTO/VO/BO/PO/Entity 及 Mapper；
- 表、字段、索引、缓存、队列、定时 Job、配置、Feature Flag 和依赖；
- 前端 Store、Provider、Hook、Route、Page、Dialog 和 Preflight 请求。

已有元素写 `Keep`，并引用当前消费者和职责。新增元素的“直接方案不足”和“新增成本”不能留空。

## 接口必要性测试

分配新接口 ID 前回答：

1. **独立目标**——操作是否交付独立可观察的用户/系统结果，还是仅为另一个操作做机械准备？
2. **真实消费者**——指出当前或已批准消费者。它是否展示、选择、缓存、校验、分支使用结果，或具有其他独立用途？
3. **权威所有者**——哪个组件拥有该事实，该事实是否独立于目标操作变化？
4. **直接方案**——现有接口、目标接口扩展、认证上下文、路由/资源身份、本地构建数据或服务端直接查询能否满足？
5. **派生能力**——目标后端能否从 Principal、租户上下文、当前资源、持久化关系、配置或其他服务端事实安全派生？
6. **调用方已知信息**——调用方是否已从用户输入、Route State、当前记录、本地 Registry、构建产物或之前业务操作持有该值？
7. **结果用途**——调用方是否除了把结果原样复制进下一请求之外，还做了有意义的事情？
8. **交互成本**——增加多少网络往返、Loading/Error 状态、缓存、重试、权限、测试和运维信号？
9. **竞态语义**——查询与使用之间是否可能变化？哪个操作负责权威重校验？
10. **生命周期**——接口是否具有独立版本、兼容、所有权和废弃周期？

操作没有独立结果且目标操作可以自行派生/校验时，默认选择 `Merge`、`Reuse` 或 `Remove`。

## 参数所有权与派生

每个非平凡请求参数先确定所有权，再决定传输：

| 参数 | 语义所有者 | 调用方已知？ | 目标端可派生？ | 用户必须选择？ | 独立变化方式 | 传输决策 |
| --- | --- | --- | --- | --- | --- | --- |
| `<字段>` | `<用户/前端/后端/外部>` | 是 / 否 | 是 / 否及方式 | 是 / 否 | `<变化时机>` | Body / Path / 上下文派生 / 删除 |

规则：

- 基础设施已经认证的身份、租户、权限和 Service 来源事实保留在服务端，除非契约明确需要用户选择作用域；
- 不能通过 API A 返回服务端派生值，只为了让调用方再通过 API B 传回；
- 不能为了填充另一个请求而查询构建期常量、本地路由 Metadata、固定枚举或当前记录已有数据；
- 真实契约是稳定业务 Key 或当前资源关系时，不能强迫客户端先查询内部数据库 ID；
- 即使前置 Selector/Discovery 已展示可变服务端事实，目标操作仍必须重新校验；
- 不能把重大所有权决策藏在“参数来源”表格中。

## 先查询再转发反模式

默认拒绝：

```text
Frontend -> GET /operation-context
Backend  -> { tenantId, applicationId, sourceCode }
Frontend -> POST /execute { tenantId, applicationId, sourceCode, businessInput }
Backend  -> 执行前再次读取相同上下文
```

它增加延迟、两套 Loading/Error、陈旧值竞态、重复鉴权、额外客户端状态和兼容面，却没有改变用户目标。

优先选择：

1. **后端派生**

```text
Frontend -> POST /execute { businessInput }
Backend  -> 从认证或持久化上下文派生 tenant/application/source
```

2. **当前资源路由**

```text
Frontend -> POST /applications/{applicationId}/execute { businessInput }
```

只有 `applicationId` 已经标识页面/资源或来自真实用户选择时才使用；不能为了获得它新增 Preflight。

3. **合并 Command**

```text
Frontend -> POST /execute { stableBusinessKey, businessInput }
Backend  -> 原子解析内部 ID 并执行
```

4. **本地/构建期来源**

值随前端发布且无需服务端权威发现时，使用类型化本地 Registry/配置。

目标操作始终负责鉴权与校验；前置查询永远不能让不安全 Command 变安全。

## 合理的发现与选择

独立查询在以下情况下可能合理：

- 用户必须从权限过滤、服务端所有且独立变化的目录中选择；
- UI 展示 Search、Label、Availability、Status、Price、Capacity 等决策信息，而不是只转发不透明参数；
- 多个独立操作复用可缓存、带版本的目录；
- Capability/Protocol 协商会改变客户端行为，并具有明确版本/过期语义；
- Pagination/Search 使选项无法或不适合嵌入 Command；
- 运维人员把发现结果作为独立用例复核或审计。

合理时必须说明：

- 独立用例和消费者可见结果；
- 为什么本地/当前/请求上下文不足；
- 缓存及失效/过期；
- 选择身份和稳定业务含义；
- Command 时重校验和陈旧选择错误；
- 取消或查询失败是否阻塞用户目标；
- 为什么合并操作更差。

“前端需要这个 ID”不是独立用例。

## 交互成本与竞态分析

比较设计前后的关键用户路径：

| 路径 | 网络调用 | 新客户端状态 | 新服务端契约/状态 | 失败/竞态点 | 用户可见价值 |
| --- | --- | --- | --- | --- | --- |
| 直接基线 | `<数量>` | `<loading/error>` | `<元素>` | `<点>` | `<结果>` |
| 拟议方案 | `<数量>` | `<状态>` | `<元素>` | `<点>` | `<新增价值>` |

只计算业务路径调用，不算静态资源加载。重试和缓存命中单独说明。如果调用和失败点增加，却没有已批准的正确性、安全、可用性或运维收益，必须拒绝。

Fetch-Then-Command 必须定义 TOCTOU：

```text
T1 查询返回选项/版本 V
T2 权威状态变为 V+1
T3 Command 提交 V
T4 Command 必须拒绝、刷新或应用明确允许的版本规则
```

不能把 Preflight 响应当作 Command 时鉴权。

## 完整决策示例

### 拒绝机械参数接口

| 关注点 | 决策 |
| --- | --- |
| 变更分类 | 拟新增 `GET /current-application-context` |
| 独立消费者目标 | 无；结果不展示、不选择 |
| 参数所有权与派生 | 租户/应用已经存在于认证 Principal 和持久化路由资源 |
| 直接/零新增接口方案 | 目标 Command 派生两者，只接收业务输入 |
| 调用方使用结果 | 原样复制字段进入 Command |
| 往返与失败点 | 增加一个 RTT、Loading/Error、缓存/竞态、鉴权/测试面 |
| 结论 | `Remove`——后端派生支配该方案 |

### 接受用户可见 Selector

| 关注点 | 决策 |
| --- | --- |
| 变更分类 | 复用现有分页应用目录查询 |
| 独立消费者目标 | 管理员依据名称/状态/所有者搜索并选择 ACTIVE 应用 |
| 参数所有权与派生 | 目录由服务端所有并独立变化；Command 无法推断用户选择 |
| 直接/零新增接口方案 | 把完整目录嵌入 Command/Route 会陈旧且无界 |
| 调用方使用结果 | 展示选项并记录明确人工选择 |
| 往返与失败点 | 一个可缓存查询；Command 重校验并返回陈旧/禁用冲突 |
| 结论 | `Keep`——独立选择价值已证明 |

### 拒绝猜测性抽象

| 拟议元素 | 现有/直接方案 | 证据 | 结论 |
| --- | --- | --- | --- |
| 只有一个 Strategy 的 `ExecutionStrategyFactory` | 现有协作者上的直接 Service 方法 | 没有当前变化点或第二实现 | Remove |
| 有界本地查询的新缓存 | 已有索引数据库查询 | 无延迟/容量证据，失效反而增加状态 | Remove |
| 与内部稳定响应模型完全相同的新 DTO | 复用现有契约类型 | 所有权、暴露、校验、生命周期和版本一致 | Reuse |

## 最终简洁性门禁

Spec 通过复核前必须确认：

- 每个拟议元素都有需求或必要基础设施理由及明确 `Add/Keep/Merge/Remove` 结论；
- 首先评估直接/零新增元素基线；
- 不存在只返回另一个接口可派生参数或调用方原样转发参数的接口；
- 每个新接口都有独立消费者目标，或已证明的发现/选择/协商理由；
- 每个新类通过类必要性测试；每个模式都有当前变化点；
- 交互次数、Loading/Error、失败点、缓存/失效和 TOCTOU 可见；
- 猜测性未来扩展不能压过当前复杂度；
- 已选方案是满足已批准需求的选项中移动部件最少的方案。

如果更直接的设计用更少契约/状态满足同一需求，而 Spec 没有实质理由拒绝它，返回 `REVISE`。
