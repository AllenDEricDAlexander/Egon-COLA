# Maintainer acceptance scenarios

Use these scenarios after changing this skill.

1. **Major public-contract ambiguity**: “Add a payment callback.” The repository has two authentication styles and no callback semantics. Expected: ask the user with evidence/options; keep the Spec `Draft` and blocked; do not invent a public contract.
2. **Small naming gap**: The module consistently uses `*ApplicationService`, but the requested class name is omitted. Expected: follow the convention, record it only if consequential, and do not interrupt the user.
3. **Accepted predecessor**: A new requirement changes one endpoint field from an accepted dated Spec. Expected: create a timestamp-named later Spec with an `Amends` link and exact sections; do not rewrite the predecessor.
4. **Legacy predecessor path**: The authoritative design lives under `docs/superpowers/specs`. Expected: reference that relative path in RFC metadata; do not require a special ID or copy it into `docs/egon/spec`.
5. **Backend-only repository with no frontend concern**: The affected module has no frontend code or consumer. Expected: keep the frontend chapter and state evidence-backed `N/A`; when a frontend exists but is unchanged, use `Unchanged` instead.
6. **Cross-layer mismatch**: The interface marks a field nullable while the database design uses `NOT NULL`. Expected: self-review returns `REVISE` until reconciled.
7. **Incomplete detailed design**: The Spec lists package names but omits files, symbols, field mappings, or unit tests. Expected: review failure until exact target tree and traceability are complete.
8. **Pattern pressure**: The request asks to “use design patterns,” but there is no variation point. Expected: document that direct code is simpler; do not add an interface/factory solely to name a pattern.
9. **Filename collision**: Two Specs are created in the same minute. Expected: use distinct, more-specific kebab abstracts; never overwrite.
10. **Simple internal CRUD model**: PO, DTO, BO, Entity, and VO would have identical semantics and never cross an external boundary. Expected: apply the class-necessity test and reuse the repository-standard type where safe; do not generate a class and mapper per layer.
11. **Persistence/public boundary**: An ORM Entity contains audit, tenant, lazy relation, and internal status fields, while the endpoint exposes a stable subset. Expected: keep the Entity internal and design only the necessary Request/Response or DTO/View Object boundary types.
12. **Ambiguous DO/VO vocabulary**: Existing modules use `DO` inconsistently and use `VO` for frontend views. Expected: state the chosen local meaning, avoid introducing a conflicting `DO` definition, and keep `VO` as View Object.
13. **Persistence base class**: The repository already has a stable `BaseEntity` for ID, audit timestamps, tenant ID, and optimistic versioning. Expected: PO/ORM Entity inheritance may be selected after documenting ORM, equality, serialization, migration, compatibility, and test implications; it is not mandatory for unrelated persistence objects.
14. **Business-service reuse**: Two classes in `biz.service.impl` share calculation logic. Expected: extract and compose a calculator/policy/strategy collaborator; do not introduce `BaseBusinessService` solely for protected helper reuse.
15. **Service implementation placement**: A proposed tree places `biz.impl` beside `biz.service`. Expected: review fails until the tree uses `biz.service.impl` and maps each implementation to its Service interface.
16. **Controller bypasses Service**: A Controller injects DAO or a concrete implementation directly. Expected: review fails; the Controller must depend on the Service interface and persistence stays behind `service.impl`.
17. **Existing non-three-layer module**: The affected module follows DDD, COLA, hexagonal, or a custom architecture. Expected: preserve the existing structure and ask before a structural migration; do not silently force the three-layer profile.
18. **Simple three-layer CRUD**: The task is ordinary CRUD with no real domain abstraction need. Expected: use Controller, Service, `service.impl`, DAO, and only justified POJO roles; do not add aggregates, domain services, or repository ports.
19. **Complex multi-system conclusion**: A frontend action crosses Gateway, two services, a database, cache, and an asynchronous event consumer. Expected: classify `Complex`; trace current chains and ownership, enumerate happy/failure/retry/duplicate paths, analyze consistency and compatibility, and derive conclusions through evidence-to-verification chains before selecting the architecture.
20. **Simple local change stays simple**: One existing internal validation rule changes in one Service with no contract/schema/permission effect. Expected: classify `Simple`, inspect the exact caller and tests, and produce the direct design without ceremonial scenario/quality matrices or extra abstractions.
21. **Three architecture levels**: A Complex Spec contains only a component list and one generic diagram. Expected: review fails until System Architecture, High-Level, and Detailed Design are distinct and the Spec includes separate architecture flowchart, critical-flow flowchart, and swimlane/sequence views with failures.
22. **Inventory-only HTTP design**: The interface table lists `POST /orders` with `CreateOrderRequest -> OrderResponse`, but no per-interface section exists. Expected: review fails; expand the exact route, every input rule, full success/error payload, logic, frontend handling, compatibility, and tests.
23. **Abbreviated response JSON**: A response example says `{ "data": { ... } }` or names only `OrderResponse`. Expected: review fails; show the actual response wrapper and complete nested `jsonc`, with a line-end meaning comment for every field.
24. **Ambiguous request rules**: An input field is documented as “optional string” without null/blank/default/length/enum/cross-field behavior. Expected: review fails until all applicable validation and semantic rules are explicit.
25. **Non-HTTP contract**: An RPC method and event topic are given made-up URLs to fit an HTTP template. Expected: remove the URLs and document exact service/method or topic/key/schema/deadline/delivery/retry/deduplication semantics instead.
26. **Table-list-only database design**: A Spec lists `orders` and `order_items` with a few columns but no ownership, lifecycle, complete field semantics, relationships, access patterns, migration, or transaction design. Expected: review fails until every table is expanded.
27. **Speculative index**: A new `(status, created_at)` index is proposed without naming the query, cardinality, ordering, existing indexes, write cost, or verification. Expected: reject or fully justify it against a real DAO/SQL access path and planned `EXPLAIN`/test evidence.
28. **Historical-data migration**: A new non-null column is added to a populated table. Expected: define data profiling, default/backfill/nullability order, batching/restart, old/new application compatibility, lock risk, verification, rollback limits, and exactly one new immutable migration where repository policy requires it.
29. **Cross-section field mismatch**: `API-001` returns a nullable decimal string, the POJO uses non-null `BigDecimal`, the database uses integer cents, and the frontend expects a number. Expected: review returns `REVISE` until type, precision, nullability, mapping, JSON representation, and tests agree.
30. **Grouped CRUD interface family**: One inventory ID represents list/create/update/delete/status URLs. Expected: review fails; assign one ID to each atomic Method + URL and expand every operation, while referencing shared schemas or rules where safe.
31. **Principles without analysis artifacts**: A Complex Spec repeats architecture principles but has one current-chain row, one happy-path scenario, and no conclusion chain. Expected: strict validation fails; add multiple boundary evidence rows, materially distinct failure/recovery scenarios, quality constraints, and evidence-to-decision conclusions.
32. **Early solution anchoring**: The author draws a target architecture before tracing current registration, consumers, writes, and failure behavior. Expected: return to discovery/current-chain passes, distinguish evidence from inference/runtime claims, then derive the target delta.
33. **Shallow per-interface headings**: `API-001` has the six headings, but the request says only “DTO input,” success says only “standard wrapper,” errors say “handled globally,” and logic has two sentences. Expected: review fails; expand parameter rules, actual commented payloads, seven ordered behavior categories, compatibility, and named tests.
34. **Complete mutation contract**: A POST interface identifies its verified route, security/tenant/idempotency context, all Header/Body rules, complete request/success/error `jsonc`, ordered logic, frontend state transitions, compatibility, and tests. Expected: the contract-depth gate passes if fields also agree with model/database/frontend sections.
35. **Complete list contract**: A GET list endpoint uses a separate ID and defines page/cursor base, limits, filters, sort/tie-breaker, empty array/page behavior, full paging JSON, count/query cost, concurrency semantics, index, frontend states, and tests. Expected: pass the interface detail review; do not reuse only the create/detail response class name.
36. **Table headings without design**: A table detail contains the seven headings but lists only Java field names and says “add an index for performance” and “Flyway handles migration.” Expected: review and strict validation fail; add native column semantics, real queries, per-index order/cost, exact migration/history sequence, transactions, and recovery.
37. **Index/query mismatch**: The Spec proposes `(status, tenant_id, created_at)` while the actual query uses tenant equality, optional status, and stable time/ID pagination. Expected: explain or change ordered keys using query/selectivity evidence, include the deterministic tie-breaker, inspect optional-filter and existing-prefix behavior, and plan `EXPLAIN` validation.
38. **Unknown production evidence**: Source migrations show a table and index, but no live database was queried. Expected: state source-only evidence and leave row count, skew, bloat, lock duration, and execution plan unverified; do not claim production proof.
39. **Depth exception misuse**: A Complex Spec uses `Depth exception:` merely to avoid analyzing known retry and failure paths. Expected: review fails; the exception is valid only with repository evidence that fewer real items exist, not as a brevity escape hatch.
40. **Line-count padding**: A long Spec duplicates diagrams, tables, and generic best practices without additional evidence or decisions. Expected: remove repetition; completeness is measured by evidence, contracts, consistency, and implementability rather than line count.
41. **Requirements without use cases**: Chapter 4 lists `REQ-*` rows but never identifies actors, goals, triggers, outcomes, or postconditions. Expected: review and v2 validation fail; add `ACTOR-*` and `UC-*` analysis using a complete table or Mermaid use-case view.
42. **Implementation diagram mislabeled as use cases**: The “use-case diagram” shows Controller -> Service -> DAO. Expected: reject it; draw actors outside a named system boundary and `UC-*` observable goals inside, leaving component calls to Chapter 7.
43. **Complete table-form use cases**: A Simple Spec uses a complete table with real actors, triggers, preconditions, main/failure outcomes, postconditions, requirements, interfaces/pages, and tests. Expected: pass without forcing a decorative Mermaid use-case diagram.
44. **Complex multi-actor use cases**: A frontend user, scheduled job, external provider, and operator participate in distinct goals/recovery. Expected: prefer a Mermaid `flowchart` with a named boundary and stable IDs, plus adjacent details for conditions and outcomes the diagram cannot express.
45. **Relational design without ER diagram**: Chapter 11 fully lists columns and indexes but has no ER view. Expected: v2 validation fails when inventory tables exist; add a Mermaid `erDiagram` covering every inventory table and relevant direct neighbors.
46. **ER/table inconsistency**: The ER diagram shows a required one-to-many database FK, but table details say the relationship is optional and application-enforced. Expected: return `REVISE` until cardinality, optionality, keys, enforcement, tenant scope, and delete/orphan behavior agree.
47. **ER diagram hides an affected table**: `order_items` is read/written and appears in the ER diagram but is absent from the table inventory/details. Expected: add it to inventory and expand it; an ER node cannot replace per-table design.
48. **Non-relational storage**: The task uses only document/event/key-value storage. Expected: keep Chapter 11 and write evidence-backed relational-ER `N/A`; use another accurate Mermaid model only if it materially clarifies the design, without forcing §11.3 deep structure when §11 is not affected.
49. **Fetch then forward**: The frontend calls `GET /operation-context`, copies `tenantId/applicationId` unchanged into `POST /execute`, and the command can derive both from authenticated/resource context. Expected: reject and remove the query; derive and revalidate in the command.
50. **Legitimate selector**: An administrator searches a server-owned, permission-filtered, independently changing application catalog, reviews name/status/owner, and explicitly selects one for an entitlement command. Expected: keep/reuse the selector, define cache/expiry and stale-selection revalidation, and record its independent user goal.
51. **Fixed metadata preflight**: A frontend fetches enums, routes, or field names that ship with the same build only to construct another request. Expected: use the typed local registry/configuration and remove the preflight unless an approved server-authoritative variability requirement exists.
52. **Backend-derived context**: A proposed Request contains tenant, actor, or service-source fields already authenticated by infrastructure. Expected: remove them from caller input and derive them in the target backend; do not add a context endpoint.
53. **Speculative abstraction**: One implementation exists, but the design adds a Strategy factory, cache, event, and extension table for possible future variants. Expected: choose direct composition and current storage; add elements only when a present approved requirement proves the baseline insufficient.
54. **Interaction-cost regression**: A proposal changes one command call into lookup -> validation -> command without additional user-visible value. Expected: return `REVISE`; document calls, loading/error states, TOCTOU, cache, retries, and select the direct path.
55. **New interface necessity section missing**: An API detail fully documents its route and JSON but omits the necessity/direct-alternative decision. Expected: strict validation fails; completeness after invention is not proof that the interface should exist.
56. **Missing bundled reference**: `SKILL.md` names `references/minimal-design-and-interface-necessity.md`, but the file is absent from the installed skill. Expected: resource-integrity preflight fails before repository analysis or Spec drafting and reports the referring file, line, and missing path; the agent must not improvise the rules.
57. **Ambiguous nested reference**: A document under `references/` instructs the agent to read a bundled file by the bare name "pojo-modeling.md". Expected: resource-integrity validation fails and requires the canonical skill-root-relative `references/pojo-modeling.md` form.
58. **Repository instruction is not bundled**: The skill tells the agent to read applicable `AGENTS.md` files from the target repository. Expected: resource-integrity validation treats this as an allowed repository-scoped instruction rather than requiring an `AGENTS.md` inside the skill package.
59. **DAO-only query correction**: One Mapper/DAO predicate changes while the Controller route/JSON, Service signature and business semantics, database schema/relationships, and frontend behavior remain stable. Expected: mark DAO/query and focused tests `Affected`, the Service implementation and relevant access path `Context-only`, surrounding contracts/schema/frontend `Unchanged`; fully design only the query, bindings, ordering/paging, mapped result, failures, index evidence, and tests. Do not reproduce Controller payloads, full Service architecture, unrelated POJOs, complete tables, ER diagrams, or page trees.
60. **Existing layer is unchanged, not absent**: A DAO-only task runs in a module that has a Controller and frontend consumer, but neither changes. Expected: use `Unchanged` with exact evidence and preserved invariants; do not write `N/A`, and do not expand their target design.
61. **Required scope expansion**: Repository evidence shows the requested DAO result cannot change without modifying the Service contract and public response semantics. Expected: record the additional affected areas and stop for user approval before widening the design; do not silently redesign the API and do not pretend DAO-only is implementable.
62. **Simple cross-layer change**: A small field rename genuinely changes Controller input, Service mapping, DAO binding, and frontend form. Expected: remain `Simple` if decision risk is low, but mark all four areas `Affected` and fully design each changed contract/field; proportional depth is not permission to omit real impacts.
63. **Existing Spring/Egon capability**: A requirement can be implemented by a Spring Boot Starter or existing Egon-COLA Component, but the draft proposes a custom framework/helper. Expected: `MC-REUSE-001`/`MC-DEP-001` fail; select the existing capability or document a proven gap and approved dependency/implementation impact.
64. **Allowed architecture selection**: The project was generated from `egon-cola-archetype-service`, but the draft adds a sibling `biz.service.impl` module. Expected: `MC-ARCH-001` fails; preserve the exact `common/facade/domain/application/infrastructure/adapter/starter` contract and verifier. A traditional project must conversely reject invented COLA modules.
65. **Ambiguous Java carrier**: A new `UserInfo`, `OrderData`, `SearchParam`, or `CacheBean` is proposed. Expected: `MC-NAME-001` fails until the type is named for its actual DTO/VO/BO/Query/Command/Event/PO or behavior responsibility.
66. **Reusable boundary input**: One Command supports create and update with different required fields. Expected: design Jakarta Validation Groups, `@Validated` group invocation, nested `@Valid`, error mapping, and `ValidationUtils` reuse; do not duplicate the Command or handwrite repeated null checks.
67. **Telephone normalization**: A boundary accepts international telephone numbers. Expected: design libphonenumber (or an already approved equivalent) parsing, region source, E.164 normalization, validity/error behavior, and tests; a handwritten regex/custom validator without a proven framework gap fails `MC-VALID-001`.
68. **Data representation and conversion**: A simple immutable DTO is designed as a mutable class with all Lombok annotations and manually copied through Service setters. Expected: use a Record/compact constructor for the Simple object and MapStruct/MapStructPlus plus mandatory Egon `BaseConverter`; fail `MC-MODEL-001` and `MC-CONVERT-001` otherwise.
69. **Spring Bean injection contract**: A new business Service uses field `@Autowired`, implicit Bean names, or unqualified dependencies. Expected: require `@Slf4j`, explicit stable Bean names, final fields, `@RequiredArgsConstructor`, `@Qualifier` on every dependency, and evidence that `lombok.config` copies Qualifier.
70. **Configuration drift**: One profile adds a new core key that other environment files lack. Expected: `MC-CONFIG-001` fails until all profiles have the same structure/key set with environment-specific values and a typed `@ConfigurationProperties` model where applicable.
71. **Manual Check blocker**: All design prose appears complete, but one applicable `MC-*` row is missing, `UNKNOWN`, `FAIL`, `BLOCKED`, or lacks evidence. Expected: strict validation rejects a PASS verdict; the Spec may use a blocked/revise verdict only with the exact action and owner recorded.
72. **Literal rules summarized away**: The Skill or generated Spec replaces the user's exact numbered block with a short English summary. Expected: literal-rule preservation tests fail; both entrypoints retain the exact block and §6.2 expands every original number separately.
73. **Controller-only validation**: The Spec validates Request input at the Controller but leaves Controller -> Service and Service -> DAO/Repository command/query handoffs undesigned. Expected: Rule 2 and `MC-VALID-001` fail until each affected crossing has constraints, group selection, invocation, errors, and tests.
74. **Optional complex-object annotations**: A Complex class selects only `@Data` and `@Builder` because the other annotations appear inconvenient. Expected: Rule 3 and `MC-MODEL-001` block; design the complete mandated baseline or report the exact constructor/framework conflict for user decision.
75. **Converter compatibility bypass**: A one-way mapper does not implement the common `BaseConverter` and uses setters instead. Expected: Rule 3 and `MC-CONVERT-001` block; no semantic-fit exception is silently inferred.
76. **Complex direct logic**: A multi-state/multi-strategy business flow is left as a switch because it is shorter. Expected: Rule 9 and `MC-PATTERN-001` block until a concrete pattern, participants, selection, failure behavior, and tests are designed.
77. **Legacy Swagger example copied into modern code**: The draft copies Springfox `Docket`, `@EnableOpenApi`, and `io.swagger.annotations.ApiOperation` from the referenced Mshuyan repository into a current Spring Boot module. Expected: reject it; verify the Boot generation and existing dependency management, select the compatible springdoc starter and `io.swagger.v3.oas.annotations.*`, or record a separately approved legacy migration boundary.
78. **Mixed annotation generations**: One Controller combines `@ApiOperation` with OpenAPI 3 `@Operation`. Expected: fail `API-GATE-007` and `MC-DEP-001`; one documented compatibility stack must own the module.
79. **OpenAPI inferred operation identity**: A REST method has no explicit `operationId`, and generated tools derive it from an overloaded Java method. Expected: require one globally unique stable lowerCamelCase `operationId` and a generated-document assertion.
80. **Swagger-only validation**: `@Schema(minLength = 1)` is documented, but runtime Bean Validation permits blank values. Expected: fail `API-GATE-005` and `MC-VALID-001`; runtime Jakarta Validation, Jackson, Java type, OpenAPI schema, example, and error mapping must agree.
81. **Generic success-only OpenAPI**: A POST command documents only `200` with `Object`. Expected: define the correct `201`/`202`/`204` or repository status, actual generic wrapper payload, all material validation/auth/conflict/rate/dependency errors, headers, security, and schemas.
82. **Fake authentication endpoint**: A `/login` method is added only so Swagger UI can display security information. Expected: reject the fake operation; define the real `@SecurityScheme`, OAuth/OpenID/bearer configuration, UI settings, and actual authentication contract owned by the security system.
83. **Annotation-only API interface**: A new interface duplicates every Controller mapping solely to hold OpenAPI annotations. Expected: reject unless it is an existing architectural Facade/API boundary and tests prove mapping, validation, and annotation inheritance without drift.
84. **REST Query with hidden write**: A GET endpoint records a durable approval/read acknowledgement or publishes a business event. Expected: fail CQRS and HTTP safety gates; model the behavior as an explicit Command or remove the mutation.
85. **Ceremonial CQRS expansion**: A three-layer CRUD feature adds separate databases, a command bus, event sourcing, and handler factories because the API is labeled CQRS. Expected: use L0/L1 unless current scale, consistency, security, or history evidence proves higher separation and all synchronization/recovery costs are designed.
86. **GraphQL documented as one transport route**: The Spec lists one `POST /graphql` row but no root fields, SDL, operations, variables, selection, or resolvers. Expected: assign one API contract per affected `Query.field`/`Mutation.field`/`Subscription.field` and expand the GraphQL schema/behavior.
87. **Swagger annotations on GraphQL resolvers**: Resolver methods use `@Operation` as the only documentation. Expected: reject it; SDL plus named operation documents are authoritative, while springdoc/OpenAPI applies only to actual REST operations.
88. **GraphQL N+1 and authorization gap**: A nested list field loads each child individually and only the shared `/graphql` path is authenticated. Expected: design `@BatchMapping`/DataLoader or prove bounded direct loading, plus field/Service authorization, cost limits, missing-item/null/error behavior, and `GraphQlTester` coverage.
89. **REST/GraphQL behavior divergence**: The REST command validates tenant and idempotency but the GraphQL mutation calls a separate implementation without those checks. Expected: return `REVISE`; both protocol adapters must delegate to one business behavior and map the same outcomes.
90. **API gate incomplete**: Chapter 9 has detailed contracts but omits one `API-GATE-*` row, uses `UNKNOWN`, or marks REST/GraphQL `N/A` while that protocol appears in inventory. Expected: strict validation rejects final PASS and Chapter 20 `MC-BLOCKER-001` must remain failed/blocked.
